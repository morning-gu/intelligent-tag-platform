# 动态标签生成方案

> 说明对象：影视资产 → 自动生成中文语义标签（开放式生成，`mtg-v3` 口径）。
> 本文只讲**逻辑与顺序**，不涉及具体代码文件与函数实现。
> 涉及内部叫法时，第一次出现都会解释。

---

## 0. 先统一几个名词

| 名词 | 含义 |
|---|---|
| **资产** | 一部影片在平台里的一条记录，核心是它的"识别内容"。 |
| **识别内容（内容 JSON）** | 一部片的结构化描述：片名、时长、整片中文摘要、人物表，以及按剧情切好的若干**场景**；每个场景带时间区间、中文描述、氛围、人物情绪、地点、台词等。它是标签生成的唯一输入。 |
| **场景** | 内容 JSON 里的一段剧情片段，有起止时间和一句文字描述，带唯一编号。 |
| **关键帧** | 从数据集里挑出的画面截图，用来让模型"看见"画面，而不是只读文字。 |
| **标签库** | 平台已有标签的集合。标签本体（名字、释义、别名）与它所在的**目录**分开存。 |
| **目录** | 标签的归属位置，是一个树状结构。分两类：**静态目录**（取值固定，不允许新增标签）与**动态目录**（允许审核后扩充新标签）。 |
| **可扩展目录** | 即"动态目录"，是本次生成里新标签唯一允许落脚的地方。 |
| **维度** | 标签的类别，固定五类：风格、情绪、主题、叙事、角色。生成时要求每类都要覆盖。 |
| **挂载点** | 一个标签最终作用在谁身上：整部影片、某个场景、或某个人物。 |
| **证据** | 支撑这个标签的具体场景（场景编号 + 时间区间 + 一句场景描述），审核时给人看。 |
| **候选** | 模型生成出来、还没入库的标签草稿。 |
| **分档** | 把候选与标签库比对后的结论，三档：同名（重复）、疑似（可能同义）、新词。 |
| **判定（judge）** | 第二次调用模型，逐条检查"内容是否真的支持这个标签"，与生成是两次独立调用、两个不同模型。 |
| **审计** | 每个任务落一份 JSON，记录全过程：每轮原始候选、合并结果、判定、淘汰原因、库内对齐结论、tokens、耗时。 |

## 1. 整体流程（一条线）

```
① 生产任务被创建
      ↓
② 取资产的识别内容 + 规划关键帧
      ↓
③ 构造提示词（内容文本 + 关键帧图片 + 库内已有标签 + 可扩展目录清单 + 生成要求）
      ↓
④ 多轮生成（同一提示词跑 3 轮，各自独立出候选）
      ↓
⑤ 解析每轮输出 → 候选清单
      ↓
⑥ 跨轮合并（同名归并 + 语义相近的聚类）
      ↓
⑦ 逐条判定"内容是否支持"（第二次模型调用）
      ↓
⑧ 过滤（不支持的、没证据的、证据不够的淘汰）
      ↓
⑨ 与标签库对齐（同名 / 疑似 / 新词）+ 疑似项二次复核
      ↓
⑩ 排序 + 截断（限额）
      ↓
⑪ 给每条标签定目录与挂载点
      ↓
⑫ 新词补写通用释义
      ↓
⑬ 落库到"待审核队列"（命中库内标签的直接生效）
      ↓
⑭ 人工审核通过 → 正式成为库内标签并挂到资产上
```

---

## 2. 输入：生成任务拿到什么

创建生产任务时，至少要指定：**哪部资产**、**生成模式**（本文只讲"开放式"）、**生成策略**（可选）。

生成开始前按顺序做四件准备工作：

**2.1 取内容**

从资产记录里读出识别内容。如果资产不存在，或它的识别内容为空（还没导入识别结果），任务直接判定失败，不进入生成——不存在"拿空内容硬生成"的情形。

**2.2 规划关键帧**

为每个场景挑若干张关键帧（默认每场景 2 张，全片上限 24 张）。
挑选依据是数据集里"这一场景对应的镜头号区间"，在该区间内等距取帧。
若某场景取不到帧，不是错误，该场景退化为纯文字。

**2.3 读标签库**

把标签库读成内存索引（只读，绝不回写）。三件事会用到它：
- 给模型一份"库里已经有哪些标签"的名字清单（避免重复造词）；
- 给出"允许新增标签的目录"清单（决定新词能落在哪）；
- 生成结束后用它的向量做"候选 vs 库内"的相似度比对。

**2.4 解析策略**

策略决定硬边界，主要有四项：允许在哪些目录范围内产出、最多产出多少条、是否允许产出新词、单目录最多产出几条。策略为空时用默认值。

---

## 3. 第 1 步：构造提示词

一次请求由五块内容拼成，顺序固定：

### 3.1 内容正文（文字部分）

按固定格式把识别内容渲染成文本：

```
电影：《片名》
摘要：整片中文摘要（截断）
人物：角色A（演员）、角色B（演员）…（截断）
- 场景编号 [起止毫秒] 场景描述（截断）
  氛围：场景情绪列表
  人物情绪：角色（情绪）、…
  地点：某地
  音乐：某种音乐
  台词：说话人（语气）：台词原文
  …
```

原则：**只输出模型需要判断的信息，且全部来自内容 JSON 本身**。没有的字段就整行不出现（例如没有音乐就不写"音乐："）。

### 3.2 关键帧（图片部分）

对每个场景，依次插入"〔关键帧〕场景编号 第 n/N 张"的文字标注 + 图片本体。
图片与文字混排在同一个请求里，模型看图时知道每张图属于哪个场景。

### 3.3 库内已有标签清单（可选）

给一份名字列表，措辞刻意留了口子：

> 这些标签库里已经有了，不要原样重复输出；如果认为某条对这部片不够准确、不够具体，可以给出更精确的说法。

也就是说：**库里有的词不许照抄，但允许"更细一层"的新说法**（库里有"悬疑"，仍可产出"悬疑解谜"）。

### 3.4 可扩展目录清单（可选）

列出所有"允许新增标签"的目录，每行：`目录 id｜目录全路径｜该目录支持的挂载点`。
并明确要求：**只能从这里选目录 id，不许自造；实在没有合适目录的标签，宁可不输出**。

这一步的意义：让"标签落在哪个目录"在**生成时**就由模型一并给出，而不是生成完再用向量去猜。

### 3.5 生成要求

核心约束（按原文顺序）：

1. **维度**：围绕五个维度（风格/情绪/主题/叙事/角色）生成 15–20 个中文标签，不受既有词表限制。
2. **两个层级**：
   - 全片级：全片共有的特征，**必须至少两个场景共同支撑**，写成 2–8 字的概括短语（如"阶级与偏见"），不许写成剧情描述；
   - 场景级：只属于个别场景的特征，允许单场支撑，但同样要提炼成 2–8 字短语，且**不许复述剧情**（写"狼狈闯入"，不写"泥泞跋涉的狼狈闯入"）；每场景最多一条、合计最多 5 条。
3. **长度**：所有标签不超过 8 个字。
4. **释义（desc）**：每条给一句 10–32 字的**通用释义**，解释"这个词本身指什么"，像词典条目；**不能出现片名、人名、具体剧情**，不能写"本片/这部片"。
   - 释义与"依据"是两件事：释义讲"这个词是什么"，依据讲"本片哪里能看出来"。
5. **配额**：全片级不少于 10 条，场景级最多 5 条；凑不出第二个场景支撑的，就老实标成场景级，不许编造场景。
6. **硬性约束**：
   - 每条必须能从上面的内容和关键帧找到依据，不许凭片名或常识编造；
   - 要具体、可判别，不要"好看""精彩"这类空泛词；同一含义只出现一次；
   - 引用的场景编号只能是正文里出现过的，对不上就给空数组；
   - 只输出一个 JSON 对象，形如
     `{"tags":[{"tag":"…","scope":"film|scene","dimension":"…","desc":"…","scenes":["场景编号"],"reason":"20 字以内的依据", "dir":"目录 id"}]}`，不要解释、不要代码块。

---

## 4. 第 2 步：多轮生成

同一份提示词（同一批图片）**独立跑 3 轮**。每轮是一次完整的模型调用，输出互不影响。

为什么多轮：单轮生成的覆盖面有限，且模型每次给的措辞不同；多轮后用"并集 + 合并"提高召回，同时用"重复出现"作为稳定性的信号。

每轮的输出都被单独解析成候选清单，记下每条属于第几轮。

**解析规则**：期望顶层是 JSON 对象里的 `tags` 数组（也容忍被代码块包裹、或外面多包一层对象）；逐条校验字段——名字非空（过长截到 20 字）、维度必须能识别成五类之一、层级必须能识别成全片级/场景级、场景编号合法；单轮候选数超过上限（20 条）就截断。某一轮解析失败不终止任务——这一轮记 0 条，其余轮继续。**三轮都解析不出任何候选，任务失败。**

---

## 5. 第 3 步：跨轮合并

把所有轮的候选放到一起，做两级合并：

### 5.1 先按"归一化名字"归并

归一化 = 转小写 + 去掉所有非字母数字字符（中文保留）。归一化后完全相同的，视为同一个候选。归并时聚合：所有原始写法（将来可作别名）、出现过的维度（取多数）、出现过的层级（取多数，并列时按"全片级"更严处理）、出现过的目录（取多数）、所有引用场景的并集、出现在第几轮、第一条依据与第一条释义。

### 5.2 再做"语义聚类"

把每个候选的名字转成向量，两两算相似度；相似度超过阈值（默认 0.75）的聚成一簇，且要求**簇内任意两条都过线**（避免"A 像 B、B 像 C，就把 A 和 C 硬并在一起"）。

每簇选一个**代表词**，规则依次是：出现轮数多的优先 → 名字短的优先 → 最早出现的优先。
其余写法保留为这簇的**别名**（供将来"同义归并"用，不丢信息）。

合并后得到的就是"去重后的候选清单"，通常从 45–60 条原始候选降到 20–30 条。

---

## 6. 第 4 步：逐条判定（judge）

这是**第二次模型调用**，用的是另一个模型（与生成模型分离），温度 0（尽量确定）。

### 6.1 一次判完全部

把合并后的全部候选（名字 + 维度 + 生成侧理由 + 引用场景）一次性交给判定模型，要求逐条给出判决。这样做的原因：判定本身很便宜，拆成多次调用反而贵且慢。

### 6.2 判决内容

每条判决包含：

| 字段 | 含义 |
|---|---|
| `verdict` | `supported`（内容支持）/ `insufficient`（证据不足）/ `contradicted`（内容与之矛盾） |
| `importance` | `core` / `secondary` / `incidental`，这条标签对影片的重要程度 |
| `confidence` | 0–1，判定把握 |
| `scenes` | 支持该判决的场景编号 |
| `reason` | 判定的理由 |
| `quote` | **从内容原文里摘出的证据片段** |

### 6.3 判定标准

只有一条：**内容里能不能找到明确依据**。
- 拿不到证据就判 `insufficient`（保守），不许默认判"支持"；
- 不评判"这个词好不好听、是否优雅"，只判内容支持度。

### 6.4 引用必须可核对（关键约束）

`supported` 的判决必须给出 `quote`，且这段引用要能在内容正文里找到**至少 8 个连续字符**的原文（忽略标点与空白）。

做不到的，**这条判决自动降级为 `insufficient`**。
理由：模型很容易"复述生成侧给的理由"然后说"有依据"，强制引用原文，就把这种空判变成可检测的失败。

### 6.5 失败语义

判定调用失败、或输出无法解析（重试一次后仍失败）：**整个任务标记失败**，绝不允许"审核失败就当全部通过"。失败时仍会落一份审计，记录当时的候选与错误。

---

## 7. 第 5 步：过滤

对每条合并后的候选，按顺序检查；任一条不过就淘汰，并记录淘汰原因：

| 顺序 | 规则 | 淘汰原因 |
|---|---|---|
| 1 | 判定模型没有返回这条的判决 | `judge 未返回判决` |
| 2 | 判决不是 `supported` | 记下具体判决（不足/不支持） |
| 3 | 判定把握 < 0.5 | 只挡"模型自己都不确定"的，不与人工审核阈值混用 |
| 4 | 找不到任何**真实存在**的场景作为证据 | 模型编造的场景编号直接丢掉 |
| 5 | 自报层级是"全片级"，但证据只有 1 个场景 | 本质是场景级措辞被写大了 |

关于第 5 条：层级约束只用于把关，不改写候选本身的层级字段；全片级必须至少两场支撑，这是"全片特征"这个词的最低要求。

---

## 8. 第 6 步：与标签库对齐

对通过过滤的候选，逐条与标签库比对，给出三档结论。**判定顺序固定，先命中先算数**：

| 顺序 | 规则 | 结论 |
|---|---|---|
| 1 | 归一化后与库内某标签**完全相同** | 同名（重复） |
| 2 | 候选名**包含**某个库内标签名（库内名长度 ≥ 2 字，取最长命中） | 疑似 |
| 3 | 与最相近库内标签的**字符集合重合度 ≥ 0.40** | 疑似 |
| 4 | 与最相近库内标签的**向量相似度 ≥ 0.74** | 疑似 |
| 5 | 都不命中 | 新词 |

为什么要有第 2、3 条（规则匹配）：纯向量对短词不稳，"复仇之路"与"复仇"字面包含但相似度可能不高；规则先兜一层。
为什么库内名要 ≥2 字：单字标签（如"爱""仇"）会把半张表都判成疑似。

同名判定要处理一个细节：库里可能有**多个同名标签**（挂在不同目录下，"其他"就有几十个）。这时按标签编号稳定取一条，并在原因里注明有歧义，保证同一部片重跑结果一致。

### 8.1 疑似项的二次复核

规则只能判断"像不像"，不能判断"是不是同一个概念"，实测规则层准确率只有 62%（人工标注 75 条）。所以**疑似项要再做一次模型复核**：

- 一批只调一次模型（所有疑似对子放进同一个请求，最多 40 对），温度 0；
- 输入每行一对：`候选｜库内标签｜相似度`；
- 判据只有一句话：**这两个词都进标签库，审核的人会不会认为它们是重复条目、只该留一条？**
  - 判"是"的典型：`压抑沉重 / 压抑`、`古典史诗 / 宏大史诗`、`悬疑神探 / 悬疑`（同义细化，合并后信息不丢）；
  - 判"否"的三类：① 意思相反（`非线性叙事 / 线性叙事`）；② 字面像但指不同事物（`友情与背叛 / 爱情与背叛`）；③ 只共享词、主体不同（`暴君多疑 / 多疑`、`超能力觉醒 / 绝境觉醒`）。

### 8.2 复核结果怎么用

| 结论 | 处理 |
|---|---|
| 同名 | 直接当作库内标签，替换成库内标准名，挂上库内标签编号（不需要复核） |
| 疑似 + 判"是" | 替换成库内标准名，挂上标签编号，**模型原词登记为该标签的别名** |
| 疑似 + 判"否" | **改判为新词**（否则它会被一直当疑似、排在后面白白让出名额） |
| 疑似 + 复核失败/超时/解析失败 | 按"未复核"处理，**不替换**，结论写进审计 |

复核失败不阻塞任务，与判定（judge）的失败语义相反——理由是：替换错了会污染标签语义，比"没复核"更糟。

---

## 9. 第 7 步：排序与截断

### 9.1 排序键（依次比较）

1. **重要度**：core > secondary > incidental（没有判定的按最低）；
2. **库内分档**：新词 > 疑似 > 同名（同等重要时，优先保留库里没有的新词）；
3. **判定把握**：高的优先；
4. **出现轮数**：多的优先（最后才看，因为"模型爱说"不等于"对影片重要"）。

### 9.2 截断

先算限额：`min(全局上限, 策略上限)`（默认全局 15 条）。

然后分两桶各自截断：

- **命中库内标签的那一桶**（同名 + 复核确认的疑似）；
- **新词那一桶**。

两桶各自最多 `限额` 条。设计意图：命中的库内标签本来就是"库里已有的东西"，让它挤掉一条真正的新词没有道理；两桶独立，谁都不占谁的名额。

被截掉的候选不删除，全部记进审计（标明它属于哪一档），便于事后看"名额被谁用掉了"。

---

## 10. 第 8 步：定目录与挂载点

标签落在哪个目录，以及最终挂到谁身上，是两件独立的事。

### 10.1 命中库内标签的

直接用该标签在库里的目录；挂载点按目录声明的适用范围解析，三种粒度：

- **整片**：挂到这部资产本身；
- **场景**：挂到证据里第一个真实存在的场景；
- **角色**：挂到证据场景里**唯一**出现的角色——证据场景里出现多个角色时解析不出唯一挂载点，这条淘汰（宁可少一条，也不猜它是谁）。

解析不出唯一挂载点的，这条淘汰。

### 10.2 新词：先看模型指定，再回退

**① 模型在生成时给的目录**（主路径）。校验依次为：

1. 能否解析：允许是目录 id、目录全路径、或唯一的目录名；
2. 是否在本次生成允许的范围内；
3. 目录是否存在；
4. 目录是否是"允许新增标签"的动态目录；
5. 该目录是否已达本次产出配额；
6. 按目录的适用范围能否解析出唯一挂载点（否则这个标签挂不上任何东西）。

任何一步不过，**不静默改写**，而是记下原因、转到第 ② 步。

**② 回退：按语义找目录**。把候选名转成向量，与"各目录的描述"算相似度，从高到低逐个试，同样要过配额与挂载点检查，第一个通过的就用。目录来源会标注为"回退"，审核页能看出这条不是模型选的。

两步都失败的，淘汰并记录原因。

---

## 11. 第 9 步：补写通用释义

生成阶段给的释义（desc）有时不合规：写了剧情、出现片名或人名、或干脆没写。

处理方式：**只对新词**做检查——凡是"不是通用释义"的都收集起来，一次性批量请模型重写（给出标签名 + 所属目录路径，要求写成词典式释义、不含本片信息）。

补写不出来的，**留空**。原则：宁可没有释义，也不把某部片的剧情当标签释义写进库。

---

## 12. 第 10 步：落库（输出流向）

生成结果不是直接进标签库，而是先进**待审核队列**（表名 `pre_asset_tag`，一行 = 一条候选标签在该资产上的申请）。

### 12.1 两种行

| 类型 | 内容 | 状态 |
|---|---|---|
| 命中库内标签（同名/复核确认的疑似） | 指向库内标签编号，记录别名候选 | **直接通过**，系统留痕说明是"同名自动通过"还是"系统自动并入" |
| 新词 | 候选名、候选释义、候选目录、证据 | **待审核** |

直接通过的行会**同时**写入正式挂载关系（资产 ↔ 标签），即立刻生效。

### 12.2 重跑语义

同一资产、同一生成模式下，**尚未审核的旧候选先被清掉**再插入新候选——不会在队列里越积越多。已经审核定稿的行不受影响（不复活、不覆盖）。

### 12.3 别名登记

疑似被复核确认、并入库内标签的那些，模型原词会登记为该标签的**别名**，并写一条变更日志。失败只告警，不影响任务结果。

### 12.4 事务边界

生成的产出与任务终态（成功/失败、耗时、模型版本、口径版本）在**同一个事务**里提交。任何环节抛错则整体回滚，任务记为失败——不会留下"标签写了一半、任务还显示成功"的中间状态。

---

## 13. 第 11 步：人工审核

审核队列里的一行，可以执行四种动作：

| 动作 | 效果 |
|---|---|
| **通过** | 新词写进标签库（生成标签定义 + 在目录下建立节点）；然后写正式挂载关系 |
| **拒绝** | 该行定稿为拒绝。拒绝是终态语义：以后重跑不会为同一个候选再生成一行 |
| **修改** | 改候选名 / 释义 / 归属目录，然后再走通过逻辑；修改后仍按"通过"入库 |
| **合并** | 把这条候选并到库里已有的某个标签上（记为别名），不再新建标签 |

通过时的二次校验（与生成侧重复，但必须再挡一次，因为中间可能有人改过目录）：

1. 目录必须存在；
2. 目录必须是**动态目录**（静态目录的取值固定，不允许扩充）；
3. 候选行的挂载粒度必须在该目录声明的适用范围里；
4. 目标标签必须存在于标签库。

全部满足才写库；任一条不满足，审核动作报错，**零副作用**（校验全部先于任何数据变更）。

## 14. 参数与默认值（当前口径）

| 参数 | 默认 | 作用 |
|---|---|---|
| 生成轮数 | 3 | 同一提示词独立生成的次数 |
| 每场景关键帧 | 2 | 送进模型看的画面数 |
| 全片关键帧上限 | 24 | 控制单次请求体积 |
| 单轮候选上限 | 20 | 一轮最多收多少条候选 |
| 合并相似度阈值 | 0.75 | 语义聚类的门槛 |
| 判定把握下限 | 0.50 | 低于此值直接淘汰 |
| 最终标签上限 | 15 | 落库条数上限（两桶各自） |
| 库内相似度阈值（疑似） | 0.74 | 向量判定"疑似"的门槛 |
| 字符重合阈值（疑似） | 0.40 | 规则判定"疑似"的门槛 |
| 库内标签提示条数 | 30 | 提示里给模型看多少条已有标签 |
| 可扩展目录上限 | 60 | 提示里列多少个可放新标签的目录 |

## 15. 各环节失败语义（一张表）

| 环节 | 失败时 |
|---|---|
| 资产不存在 / 无识别内容 | 任务失败，不生成 |
| 关键帧取不到 | 不失败，该场景退化为纯文字 |
| 某一轮生成解析失败 | 该轮记 0 条，其余轮继续 |
| 全部轮次都解析不出候选 | 任务失败 |
| 判定（judge）调用或解析失败 | **任务失败**，绝不静默放行 |
| 疑似复核失败 | **不失败**，按"未复核"处理（不替换） |
| 目录校验不过 | 不失败，回退到向量归类；仍不行则淘汰该候选 |
| 释义补写失败 | 不失败，释义留空 |
| 审计落盘失败 | 只告警，不影响结果 |
| 落库任一步异常 | 整体回滚，任务记失败 |

---

## 16. 一句话总结

**生成**负责"想得多"（3 轮、自由产出、每场景看图）；
**合并**负责"去得重"（同名归并 + 语义聚类）；
**判定**负责"站得住"（逐条查内容支持，且必须引用原文）；
**对齐**负责"接得上库"（同名 / 疑似 / 新词三档，疑似二次复核）；
**排序截断**负责"留得精"（重要度优先、新词优先、两桶各限额）；
**落库与审核**负责"进得去"（命中库内的直接生效，新词走人工审核，通过后才成为正式标签）。
